Provider application reviewer context contract

1. Admin provider-application review must identify the applicant with available account name and email, while retaining a shortened account id for audit disambiguation.
2. Reviewer context must show any existing Professional or Business Provider identity owned by the applicant, including display name and current verified/not-verified state.
3. A first-provider application must clearly state that no existing Professional or Business identity is present.
4. If any Provider identity already exists while another provider application is still pending, the UI must label it as a Provider identity conflict and disable approval.
5. The database review RPC and cross-table ownership trigger remain the final one-provider-per-account guards even if a stale client attempts approval directly.
6. Reject remains available for stale/conflicting pending applications and continues to require a clear reason.
7. Reviewer enrichment is read-only. It must not change verification state, services, bookings, jobs, finance, or recurrence behavior beyond enforcing the approved one-provider identity policy.
8. Provider application review remains protected by the existing Admin authorization boundary; no reviewer context becomes public or applicant-visible through this change.
