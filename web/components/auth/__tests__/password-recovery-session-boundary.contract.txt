Password recovery session boundary contract

1. `/reset-password` renders `PasswordRecoveryBoundary` before rendering the existing `ResetPasswordForm`.
2. The recovery form is authorized only after Supabase emits `PASSWORD_RECOVERY` with an authenticated recovery session.
3. A normal `INITIAL_SESSION`, including an already signed-in account visiting `/reset-password` directly, must not authorize the recovery form.
4. Recovery URL hints (`type=recovery`, recovery hash, or PKCE `code`) may keep the boundary in a short checking state, but they never authorize password reset by themselves.
5. If no valid `PASSWORD_RECOVERY` event is observed, the page resolves to the invalid-recovery UI and links back to `/forgot-password` / `/login`.
6. Existing password validation and `updatePasswordWithSupabase` behavior remain inside `ResetPasswordForm` and are unchanged.
7. `/account/security` remains the normal signed-in password/email change surface and continues to re-verify the current password before changes.
8. No Supabase database, Auth dashboard configuration, signup/login behavior, Provider identity, finance, or recurrence/recovery state machine is changed.
